# Deploying Kooks to a Linode

One 1GB Nanode running three containers: the Next.js app, Postgres, and Caddy for TLS.
Self-contained — it terminates its own TLS and depends on no other host.
Everything below is one-time except step 6, which every push to `main` repeats on its own.

## What you need first

- A Linode (see step 1)
- A subdomain you control, e.g. `kooks.example.com`
- Your `OPENAI_API_KEY`

---

## 1. Create the Linode

In [cloud.linode.com](https://cloud.linode.com) → **Create → Linode**:

| Field | Value |
| --- | --- |
| Image | Debian 12 or Ubuntu 24.04 — `bootstrap.sh` detects which and picks the matching Docker repo |
| Region | Closest to the crew (`Newark, NJ` for US East) |
| Plan | **Nanode 1GB** — $5/mo |
| SSH key | Add yours. Do not rely on a root password. |

The app idles around 400MB across all four containers, and the image is built in CI
rather than on the box, so nothing here needs build headroom. 1GB is enough; the
bootstrap script adds 2GB of swap as the safety valve.

Note the IPv4 address when it finishes provisioning.

## 2. Point DNS at it

Add an **A record** for your subdomain pointing at that IPv4 address.

Verify before continuing — Caddy's certificate request fails if the name does not
already resolve, and Let's Encrypt rate-limits repeated failures:

```bash
dig +short kooks.example.com   # must print the Linode's IP
```

## 3. Bootstrap the server

From the repo root:

```bash
scp deploy/bootstrap.sh root@<ip>:/tmp/
ssh root@<ip> 'bash /tmp/bootstrap.sh'
```

Installs Docker, creates the `deploy` user, adds swap, caps log growth, enables
`fail2ban`, and closes everything except 22/80/443. It is idempotent — re-run it
freely.

It disables SSH password authentication **only** once a key is present, so a
key-less run leaves you a way back in. If it warns about that, fix it and re-run:

```bash
ssh-copy-id deploy@<ip>
ssh root@<ip> 'bash /tmp/bootstrap.sh'
```

## 4. Generate and upload the environment

```bash
./deploy/make-env.sh              # prompts, then writes ./.env.production
scp .env.production deploy@<ip>:/opt/kooks/.env
```

The script generates the Postgres password, `SESSION_SECRET`, the seed invite token
and a fresh VAPID keypair; it asks you only for the things it cannot know. Nothing
is transmitted anywhere — you copy it up yourself.

**Keep a copy.** The VAPID keys are not recoverable from the server, and
regenerating them unsubscribes every device that has already granted permission.

The last line of its output is your way into the fresh deployment:
`https://<domain>/join/<seed-token>`.

## 5. Add the repository secrets

In GitHub → **Settings → Secrets and variables → Actions**:

| Secret | Value |
| --- | --- |
| `VPS_HOST` | the Linode's IPv4 |
| `VPS_USER` | `deploy` |
| `VPS_SSH_KEY` | the **private** key whose public half is on the box |

`VPS_SSH_KEY` must be the full PEM including the `-----BEGIN...` and `-----END...`
lines. A key generated by `ssh-keygen` without `-m PEM` is fine; a truncated paste is
the usual cause of a `handshake failed` on first deploy.

## 6. Deploy

Push to `main`, or run the **Deploy** workflow manually. It builds the image, pushes
it to GHCR, copies the compose files and `Caddyfile` up, pulls, restarts, and then
polls the app until it answers — so a container stuck in a crash loop fails the
workflow instead of showing a green tick.

The first run takes a few minutes: the image is ~1.2GB, and the container runs
`prisma migrate deploy` and the seed before `server.js`.

Then open `https://<domain>` — Caddy will have obtained a certificate on its first
request.

## Verifying it actually works

TLS and push are the two things that fail quietly.

```bash
# Certificate is real, not self-signed
curl -sI https://kooks.example.com | head -1

# SSE is streaming, not buffered. This should print `: connected` immediately
# and a `: ping` every 25s. If nothing appears for 25s, a proxy is buffering.
curl -N -H 'Cookie: kooks-session=<a real token>' \
  https://kooks.example.com/api/presence/stream
```

On the box:

```bash
ssh deploy@<ip>
cd /opt/kooks
docker compose -f docker-compose.yml -f docker-compose.prod.yml ps
docker compose -f docker-compose.yml -f docker-compose.prod.yml logs -f app
docker stats --no-stream          # memory headroom
```

Push notifications and "Add to Home Screen" cannot be verified from a terminal.
Both need a real iPhone, and iOS only permits push from an installed PWA — install
it first, then grant permission. This is the real-device pass still open in
`deferred-work.md`.

## Backups

Nothing here backs up Postgres. The data is small and mostly regenerable, but
`users`, `breaks` and `crew_members` are not — losing them means re-inviting the
crew and re-dropping every pin.

```bash
# On the server. Add to cron once you care.
docker compose -f docker-compose.yml -f docker-compose.prod.yml exec -T db \
  pg_dump -U postgres kooks | gzip > ~/kooks-$(date +%F).sql.gz
```

Linode's Backup service ($2/mo on a Nanode) covers the whole disk and is the
lower-effort option.

## Rollback

Images are tagged `:latest` only, so there is no previous tag to roll back to.
The recovery path is to revert the commit and let CI redeploy. If you want real
rollback, tag with the commit SHA in `deploy.yml` as well and pin `KOOKS_IMAGE`
to a known-good SHA.

## Things that will bite you

- **`CONDITIONS_SOURCE` must stay `swellcloud` in production.** `mock` puts invented
  surf numbers on a go/no-go screen. SwellCloud is unreachable, so conditions simply
  stay empty and the UI says so — which is the honest failure.
- **The GHCR package may be private.** The deploy logs into GHCR with the workflow's
  own short-lived token, so this is handled; if you ever pull by hand on the server
  you will need `docker login ghcr.io` yourself.
- **Do not add a `3000:3000` port mapping.** The app is deliberately bound to
  `127.0.0.1`. Publishing it broadly serves the app over plain HTTP on the public IP,
  bypassing TLS — and push subscriptions and the iOS install prompt both require a
  secure context.
