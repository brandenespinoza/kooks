# Kooks - Epic Breakdown

## Overview

This document provides the complete epic and story breakdown for Kooks, decomposing the requirements from the PRD, UX Design, and Architecture into implementable stories.

> ### Replan corrections — 2026-08-31
>
> This document was audited against the implemented tree and four defects were corrected in place. Inline `> **Correction**` blocks mark each one. Live story status is tracked in [`implementation-artifacts/sprint-plan.md`](../implementation-artifacts/sprint-plan.md) — **not** in this file.
>
> 1. **Design tokens.** `bg-[--bg]` does not work in Tailwind v4 — it compiles to invalid CSS that browsers drop silently. Tokens are registered in `@theme inline` and used as plain utilities (`bg-bg`, `bg-action`, `text-action-fg`, `text-text-secondary`, `border-divider`, `text-stale`). Applies document-wide.
> 2. **`assertCrewMember` is real from Story 1.3**, not an always-throwing stub. The original plan would have made Epics 2–4 fail closed and undemoable. See Story 1.3.
> 3. **The full 8-model schema already exists** (migration `20260901005755_full_schema`). Every "add model X via `prisma migrate dev`" AC in Stories 2.2, 3.1, 4.1, 5.1 and 6.2 is obsolete — treat those models as present. Write a migration only when a story genuinely changes the schema.
> 4. **Verdict generation is gated on the SwellCloud model run**, not on every poll — the original Story 3.2 AC contradicted FR-8 by a factor of 12. See Story 3.2.

## Requirements Inventory

### Functional Requirements

FR-1: User can create a Break by dropping a pin on a map and entering a label. The Break is immediately visible to all Crew members within 5 seconds.
FR-2: User can swipe left/right on the Break screen to move between their saved Breaks.
FR-3: User can delete a Break they created. Deletion removes the Break from all Crew members' views and voids any active Check-Ins.
FR-4a: User can designate exactly one saved Break as their Home Break. Home Break governs the dawn patrol push and night-before nudge.
FR-4b: User can save a Break created by another Crew member to their own Break list.
FR-5: Each Break screen displays a Conditions Verdict generated by an LLM from Raw Data. Maximum 10 words. Hype-friend voice.
FR-6: Raw Data (swell height, swell period, wave direction, wind speed, wind direction) is hidden by default and revealed with one tap below the Conditions Verdict.
FR-7: Conditions data refreshes automatically every 15–30 minutes per Break via scheduled SwellCloud API poll.
FR-8: Conditions Verdict is generated by calling GPT-5.4 nano (OpenAI) once per SwellCloud model update (4× daily) per Break. Verdict is cached at Break level. Fallback to raw data display if LLM call fails.
FR-9: Each Break screen surfaces curated webcam links keyed to that Break via .env. Links open in external browser. Section hidden when no links configured.
FR-10: User can check in by selecting a Break and setting an ETA. Check-In is immediately visible to all Crew members within 5 seconds. A user can only have one active Check-In at a time.
FR-11: User can change their Break selection or update their ETA at any time before expiry. Edit is reflected for all Crew within 5 seconds.
FR-12: User can remove their Check-In at any time. Removal is immediate and visible to all Crew.
FR-13: A Check-In automatically expires 2 hours after the stated ETA. Expired Check-Ins are removed from all Crew views with no user action required.
FR-14: User can generate a shareable Invite Link from within the app. Link is unique per user (persistent, not one-time-use).
FR-15: A new user who taps an Invite Link creates an account by entering a display name only. No email or password required. Inviting user and new user are immediately connected as Crew.
FR-16: Crew connection is mutual and automatic upon Invite Link onboarding. Both parties see each other's Check-Ins and Break additions immediately.
FR-17: User can remove a Crew member. Removal severs both directions of visibility.
FR-18: A push notification fires to all Crew members when a user creates, edits, or removes a Check-In. Delivered within 30 seconds. Identifies who checked in, at which Break, and at what ETA.
FR-19: A push notification fires at approximately 9pm with a plain-language preview of next-day conditions at the user's Home Break.
FR-20: A push notification fires between 5:00–5:30am with one line of current conditions at the user's Home Break.
FR-21: User can enable or disable each notification type (friend check-in, night-before nudge, dawn patrol) independently. Preference is persistent across sessions.
FR-22: There is no standalone registration page. Account creation is gated by an Invite Link. Navigating to app root without invite link does not present a sign-up form.
FR-23: Account creation requires only a display name. No email, phone number, or password.

### NonFunctional Requirements

NFR-1: Conditions data no older than 30 minutes during active use.
NFR-2: Check-In and Break creation changes visible to all Crew within 5 seconds.
NFR-3: Friend check-in push notification delivered within 30 seconds of action.
NFR-4: PWA; installs to home screen via Safari on iOS 16.4+.
NFR-5: Push notifications require home screen installation on iOS — must be communicated during onboarding without alarm.
NFR-6: LLM API key (OPENAI_API_KEY) and conditions API key (SWELLCLOUD_API_KEY) stored in .env; never exposed to the client or bundled into client-side code.
NFR-7: Friend presence data (Check-Ins, Break locations) visible only to directly connected Crew members — not public, not friends-of-friends.
NFR-8: No location tracking beyond the coordinates of user-created Break pins. App does not track device location.
NFR-9: WCAG 2.1 AA compliance. All text/background color pairs must meet contrast ratios.
NFR-10: Minimum 48px tap target on all interactive elements.

### Additional Requirements

- AR-1: Project initialized with T3 Stack (`npm create t3-app@latest kooks`) — Next.js App Router, TypeScript strict, Tailwind CSS, Prisma, tRPC; skip NextAuth.
- AR-2: Additional packages installed: `pg-boss`, `web-push`, `@ducanh2912/next-pwa`, `openai`, shadcn/ui CLI (components added per-component).
- AR-3: Docker Compose deployment: `app` service (Next.js standalone, port 3000) and `db` service (postgres:16-alpine).
- AR-4: Nginx Proxy Manager handles TLS termination upstream; Next.js app runs HTTP internally.
- AR-5: pg-boss initialized in `src/instrumentation.ts` (Next.js server startup hook) for all cron jobs.
- AR-6: EventEmitter singleton in `src/server/events.ts` using `globalThis` pattern to prevent dev HMR duplication.
- AR-7: SSE endpoint at `src/app/api/presence/stream/route.ts` requires `export const dynamic = 'force-dynamic'`.
- AR-8: All Prisma models use `camelCase` fields with `@map("snake_case")` and `@@map("snake_case")` conventions.
- AR-9: GitHub Actions CI/CD: build → push to GHCR → SSH deploy → `docker compose pull && docker compose up -d`.
- AR-10: Required env vars: `DATABASE_URL`, `OPENAI_API_KEY`, `SWELLCLOUD_API_KEY`, `WEBCAM_URLS_JSON`, `WEB_PUSH_PUBLIC_KEY`, `WEB_PUSH_PRIVATE_KEY`, `WEB_PUSH_EMAIL`, `SESSION_SECRET`.
- AR-11: VAPID keys must be generated once (`web-push generate-vapid-keys`) and stored in environment before push notifications can function.
- AR-12: Prisma schema fully defined in architecture doc — 8 models: User, Session, Break, UserSavedBreak, CrewMember, CheckIn, PushSubscription, NotificationPref.
- AR-13: `assertCrewMember(ctx, breakId)` helper must be called in any tRPC procedure accessing break-specific data.
- AR-14: `protectedProcedure` used for all tRPC procedures except invite link handler and onboarding.

### Story 1.3: Invite Link Join & Account Creation

As a new user,
I want to tap an invite link, enter only a display name, and immediately access the app,
So that I can join Kooks in under 90 seconds with zero friction.

**Acceptance Criteria:**

**Given** `prisma/seed.ts` creates a primary `User` row with `inviteToken` sourced from a `SEED_INVITE_TOKEN` env var
**When** `prisma db seed` is run on first deployment
**Then** the primary user exists in the database and their invite link (`/join/[SEED_INVITE_TOKEN]`) is functional — enabling the first crew member to be onboarded

**Given** a valid `inviteToken` exists for an existing user
**When** a new user navigates to `/join/[inviteToken]`
**Then** they see only a display name input field and a confirm button — no email, phone, password, or verification fields are present

**Given** the new user enters a non-empty display name and taps confirm
**When** the form submits via the `crew.joinViaInvite` tRPC public procedure
**Then** a new `User` row is created, a new `Session` row is created with a random UUID token, and a `kooks-session` HttpOnly SameSite=Strict Secure cookie is set on the response

**Given** the session cookie is set
**When** the user is redirected to `/`
**Then** they land on the authenticated app and `ctx.user` resolves to their User record in all tRPC procedures

**Given** `src/middleware.ts` protects all routes under the `/(app)/` route group
**When** an unauthenticated request hits any protected route
**Then** the middleware redirects to `/join-required` — a static page explaining an invite link is needed with no sign-up form

**Given** `protectedProcedure` reads the `kooks-session` cookie and resolves the session from the `sessions` table
**When** a protected tRPC procedure is called with a missing or invalid session token
**Then** it throws `TRPCError` with code `UNAUTHORIZED`

**Given** `src/server/auth/assert-crew-member.ts` exports `assertCrewMember(ctx, breakId)` with **real** crew logic
**When** any tRPC procedure imports and calls this helper
**Then** it resolves the Break, allows the request when the requesting user created the Break, shares a `CrewMember` row with the Break's creator, or has the Break in their own `UserSavedBreak`; and throws `FORBIDDEN` otherwise

> **Correction (2026-08-31):** this AC originally specified a stub that throws `FORBIDDEN` *unconditionally* until Epic 5. That is unworkable: enforcement rule 2 requires calling this helper at the top of every break-scoped procedure, so an always-throwing stub makes every Break, Conditions, and Check-In procedure in Epics 2–4 fail closed, and those epics cannot be exercised end-to-end or demoed until Epic 5 lands. The `CrewMember` model now exists (migration `20260901005755_full_schema`), so the real check is implementable here at no extra cost. Epic 5's Story 5.2 becomes a *narrowing* of working behaviour rather than a from-scratch replacement.

### Story 2.2: Break Creation & Management

As a user,
I want to create a Break by dropping a pin on a map and entering a label, delete Breaks I've created, and designate one as my Home Break,
So that I can define my surf spots and tell Kooks where to send my dawn patrol alerts.

**Acceptance Criteria:**

**Given** the `Break` and `UserSavedBreak` models already exist (migration `20260901005755_full_schema`, 2026-08-31)
**When** this story begins
**Then** no migration task is required — `breaks` and `user_saved_breaks` are present with their columns, relations and indexes

**And** `break.delete` must also null `homeBreakId` on every `User` pointing at the deleted Break — `homeBreakId` is deliberately not a foreign key (it would create a `User` <-> `Break` cycle), so the database will not do this for you

**Given** `leaflet` and `react-leaflet` are installed and the "Add Break" flow opens
**When** the map renders
**Then** an interactive Leaflet map (OpenStreetMap tiles, no API key required) is displayed; the user can tap anywhere to drop a pin and capture lat/lng coordinates

**Given** the user taps the map to place a pin and enters a non-empty label
**When** they confirm via the `break.create` tRPC mutation
**Then** a new `Break` row is created with the pin's lat/lng and label; a `UserSavedBreak` join row links it to the creating user; the Break appears in the user's swipe stack immediately

**Given** the `break.create` mutation succeeds and this is the user's first Break
**When** the mutation completes
**Then** it is automatically designated as their Home Break (`homeBreakId` set on the `User` row)

**Given** the user taps delete on a Break they created
**When** the `break.delete` tRPC mutation is called
**Then** the `Break` row is deleted; the `UserSavedBreak` row is removed; the Break no longer appears in the user's swipe stack; any active `CheckIn` rows on that Break are also deleted

**Given** the user designates a different Break as Home Break via `break.setHomeBreak`
**When** the mutation succeeds
**Then** `homeBreakId` on the `User` row is updated; only one Home Break exists at a time; the Break is visually distinguished in the swipe stack

**Given** the `SWELLCLOUD_API_KEY` is not present in the environment
**When** the app boots

### Story 3.2: LLM Conditions Verdict

As a user,
I want to see a plain-language conditions verdict of 10 words or fewer in the Break screen header,
So that I can read the go/no-go signal before my brain is fully awake.

**Acceptance Criteria:**

**Given** `src/lib/openai.ts` exports a server-only `generateVerdict(rawData)` function using the `openai` SDK with `OPENAI_API_KEY` from env

**Given** the `poll-conditions` pg-boss job writes new `rawData` to a Break **and the SwellCloud model-run timestamp differs from the stored `Break.conditionsModelRunAt`**
**When** the job completes
**Then** it calls `generateVerdict`, writes the result to `conditionsVerdict`, and updates `conditionsModelRunAt` to the new model-run timestamp

**Given** the poll returns data from the **same** SwellCloud model run already reflected in `conditionsModelRunAt`
**When** the job completes
**Then** `rawData` and `conditionsUpdatedAt` are refreshed but `generateVerdict` is **not** called and `conditionsVerdict` is left unchanged

> **Correction (2026-08-31):** the original AC called `generateVerdict` on every successful poll. Story 3.1 schedules that poll every 30 minutes, which is 48 LLM calls per break per day — directly contradicting FR-8 ("once per SwellCloud model update (4× daily) per Break"). **Given** the OpenAI API call fails for any reason

**Then** `conditionsVerdict` is set to `null` on that Break; the error is logged via pino; no unhandled exception propagates; other Breaks continue to be processed

**Given** `conditionsVerdict` is non-null on a Break
**When** the `VerdictBand` renders
**Then** the verdict text is displayed at 28px/700 weight in `--action-fg` on the navy background and does not exceed 10 words

**Given** `conditionsVerdict` is null (LLM fallback state)
**When** the `VerdictBand` renders
**Then** the raw data values (swell height, period, wind) are displayed inline in the verdict zone in muted typography — the layout does not break

**Given** the `OPENAI_API_KEY` is not present in the environment
**When** the app boots
**Then** the T3 env validation throws at startup before any requests are served
