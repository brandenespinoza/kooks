# Kooks

A surf-crew presence PWA. Crew members check in at a Break with an ETA; the crew sees it in real time. Conditions verdicts are generated by an LLM from SwellCloud data on a schedule. Auth is invite-link only — no email, no password.

> **Status note (2026-09-01).** `api.swellcloud.net` resolves but never completes a connection, and no
> working key exists for it — no conditions poll has ever succeeded against the real API. A replacement
> provider is likely needed (Open-Meteo Marine is the leading candidate: no key, and it returns all five
> fields the UI shows). Until that decision is made, set `CONDITIONS_SOURCE=mock` to run on deterministic
> synthetic conditions. Everything downstream of the fetch — the 30-minute poll, the model-run gate, the
> LLM verdict, the raw-data panel — is built and verified; only the data source is open.

Built for a crew of about four people at one break. Architectural choices assume that scale: an in-process EventEmitter for SSE fan-out, pg-boss on the same Postgres, a single self-hosted instance on its own Linode, terminating its own TLS and sharing nothing with any other host.

## Stack

Next.js 15 (App Router) · TypeScript strict · tRPC v11 · Prisma + PostgreSQL · Tailwind v4 · shadcn/ui · pg-boss · web-push

## Setup

```bash
npm install                 # runs `prisma generate` via postinstall
cp .env.example .env        # then fill in the values below
./start-database.sh         # local postgres container from DATABASE_URL
npm run db:migrate:dev      # create + apply migrations
npm run dev                 # next dev --turbo
```

### Environment

All variables are validated at startup by [`src/env.js`](src/env.js) (T3 env + Zod) — a missing one fails the boot with a clear message rather than at first use. Adding a variable means editing both the `server` and `runtimeEnv` blocks in that file **and** `.env.example`.

| Variable | Notes |
|---|---|
| `DATABASE_URL` | Postgres connection string |
| `SEED_INVITE_TOKEN` | Seeds the primary user; their invite link is `/join/[token]` |
| `SWELLCLOUD_API_KEY` | Marine conditions source |
| `CONDITIONS_SOURCE` | `swellcloud` (default) or `mock` — see the status note above. Never `mock` in production |
| `APP_TIMEZONE` | IANA name, default `America/New_York` — makes the 9pm and 5am pushes fire at local time |
| `OPENAI_API_KEY` | Conditions verdict generation — server-side only |
| `WEBCAM_URLS_JSON` | JSON map of Break label → webcam URL |
| `WEB_PUSH_PUBLIC_KEY` / `WEB_PUSH_PRIVATE_KEY` / `WEB_PUSH_EMAIL` | VAPID keys — `npx web-push generate-vapid-keys`; email must start with `mailto:` |
| `SESSION_SECRET` | 32+ chars — `openssl rand -base64 32` |

## Commands

```bash
npm run dev              # next dev --turbo
npm run typecheck        # tsc --noEmit
npm run build            # next build (validates env via next.config.js)
npm run db:migrate:dev   # prisma migrate dev
npm run db:generate      # prisma generate
npm run db:studio        # prisma studio
docker compose up --build   # full app + db stack, mirrors production
```

There is no ESLint, Prettier, or test runner configured. Verification for a change is `npm run typecheck` plus `npm run build` — use `SKIP_ENV_VALIDATION=1` when env vars are unavailable.

## Deployment

Push to `main` → GitHub Actions builds the image → GHCR → copies the compose files up → SSH → `docker compose pull && up -d` → polls until the app answers. The container runs `prisma migrate deploy` and `prisma/seed.mjs` before `server.js`, so **every schema change must ship with a committed migration**. The Prisma engine/client/schema `COPY` lines in the [Dockerfile](Dockerfile) are load-bearing — Next.js standalone output does not trace them.

Requires the `VPS_HOST`, `VPS_USER` and `VPS_SSH_KEY` repository secrets.

**Target: a 1GB Linode (Debian 12 or Ubuntu 24.04).** Three containers — app, Postgres, and Caddy terminating TLS for a subdomain. The full first-time runbook, including server bootstrap and secret generation, is in **[deploy/README.md](deploy/README.md)**.

Two constraints worth knowing before changing anything there:

- The app is bound to `127.0.0.1:3000` on purpose. Caddy reaches it over the compose network; publishing it broadly would serve the app over plain HTTP on the public IP, and both web push and the iOS install prompt need a secure context.
- The image is built `linux/amd64` only. That matches a Linode. Retargeting at an ARM host means adding `platforms:` and QEMU to the build step, or the container dies on `exec format error`.
